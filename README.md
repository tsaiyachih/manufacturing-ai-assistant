# Manufacturing AI Investigation Assistant

A prototype LLM agent that lets a production-line engineer ask, in plain
language, questions like *"M-03 has had a lot of downtime this week — why,
has this happened before, and what should we do?"* and get back an
investigation report where **every number comes from SQL and every
recommendation is cited to a maintenance document**.

Built without agent frameworks (no LangChain / LlamaIndex / LangGraph): the
agent loop, tool registry, retrieval, and citation check are plain Python on
top of the Gemini SDK, so every step is visible and testable.

> All data is **synthetic** (generated by `create_database.py` and
> hand-written markdown documents). No company data is used.

## How it works

```
Engineer's question (natural language)
    │
    ▼
investigator.py — Agent loop (max 6 steps)
    │   LLM decides which tool to call next
    │   Python checks the tool name against an allowlist, then runs it
    │
    ├── Database tools (tools.py, SQLite opened read-only)
    │     count_failures         — failures in the last N days
    │     compare_with_baseline  — recent rate vs. historical rate (Python computes the ratio)
    │     get_failure_types      — breakdown by failure type
    │
    └── search_documents (rag.py)
          maintenance manual / repair records / operation manual
          → chunk by section → embed → cosine similarity → top 3 (min similarity 0.6)
    │
    ▼
Report: Conclusion / Data / Recommended actions / Sources
    │
    ▼
check_citations() — Python compares every 【citation】 in the report with the
sources the tools actually returned; anything that wasn't retrieved is flagged
as unverified (the answer is kept, but the risk is shown explicitly).
```

## Who decides what

| LLM decides | Python is responsible for |
|---|---|
| Which tool to call, with which arguments | Allowlist check — unknown tool names are rejected |
| What to search for in the documents | Running SQL (read-only connection, no writes possible) |
| How to phrase the report | All arithmetic (counts, rates, ratios) |
| When it has enough to answer | Stop condition: `MAX_STEPS`, API error handling |
| | Recording which sources were actually retrieved, and checking the report's citations against them |

The design principle: the model is good at choosing the next step and writing
the summary, but is not trusted to calculate, to touch the database directly,
or to be the only judge of whether its sources are real.

## Quick start

Requires Python 3.11+ and a [Gemini API key](https://aistudio.google.com/)
(the free tier is enough).

```bash
pip install -r requirements.txt
cp .env.example .env              # then put your key in .env
python create_database.py         # builds factory.db (synthetic, last 90 days)
python investigator.py            # runs two example investigations
```

`create_database.py` generates data relative to *today*, and deliberately
injects an anomaly: M-03 has a cluster of overheating failures in the last
7 days. Re-run it if you come back days later and "last 7 days" queries look
empty.

## Tests

```bash
python -m pytest -q tests/
```

30 tests, **no API key and no network needed** — every LLM call is replaced
by a mock, so the tests check the Python side of the contract:

- tool allowlist rejects unknown tools; missing arguments or unknown machines return an error instead of crashing (or a misleading 0)
- database tools detect the injected M-03 anomaly in the generated data
- agent loop runs every tool requested in one step, and stops at `MAX_STEPS`
- RAG refuses to answer (without calling the LLM) when nothing is similar enough
- citation check flags sources the agent never actually retrieved
- conversation history stays unchanged when an API call fails; structured output rejects non-JSON and out-of-range values

## Project layout

```
create_database.py   synthetic SQLite failure log (5 machines, 90 days)
tools.py             read-only database tools
agent.py             M4 — agent loop with the 3 database tools
rag.py               M5 — basic RAG over knowledge/
investigator.py      M6 — agent + RAG + citation check (the main entry point)
knowledge/           maintenance manual, repair records, operation manual (synthetic)
tests/               pytest suite (mocked LLM)
learning_steps/      earlier milestones, kept to show how the system was built up
```

The project was built in six milestones; `learning_steps/` keeps the earlier,
smaller versions:

| Milestone | Topic | Files |
|---|---|---|
| M1 | LLM API basics, conversation history | `learning_steps/first_call.py`, `chat_history.py`, `chat_with_function.py` |
| M2 | Structured output with Pydantic | `learning_steps/pydantic_basics.py`, `structured_prompt.py`, `native_structured.py`, `query_parser.py` |
| M3 | Native tool calling (single call) | `learning_steps/tool_calling.py`, `tools.py` |
| M4 | Agent loop (multi-step) | `agent.py` |
| M5 | Retrieval-augmented generation | `rag.py` |
| M6 | Integrated investigation assistant | `investigator.py` |

## Known limitations

- **Synthetic data only.** Five machines, four failure types, and three short
  documents. Retrieval quality and agent behaviour have not been measured on
  real maintenance records.
- **The citation check verifies that a source exists, not that it supports the
  claim.** If the agent cites a real document for something the document
  doesn't say, the check passes.
- **Numbers inside the prose are not re-checked.** The tools compute the
  numbers, but the report text is written by the model; a copied number could
  still be altered.
- **Tool order is up to the model.** The system instruction asks it to check
  the database before searching documents, but in testing it sometimes
  searched first. Results were still correct, but the order isn't enforced.
- **Single provider.** Written against the Gemini SDK; switching providers
  means rewriting the call layer (tool declarations and response parsing).
